## 1. 总体决定与设计边界

1. **一套浏览器，多种业务属性**：公司/个人工作区均使用统一文件浏览器；左侧为工作区与模块虚拟入口，中间为可导航的文件夹/文件列表，顶部为全局搜索、路径面包屑和上下文操作栏，右侧为可收起的详细信息面板。项目、合同、知识产权、企业资质等使用统一浏览和选择方式，特定字段在详细信息面板/专业编辑对话框中维护。
2. **OneDrive 为交互参考，不复制其代码和商标**：尽量一致的列表、选中高亮、复选框、右键菜单、顶部命令栏、双击打开、批量选择、移动/复制、排序、文件预览及版本历史。使用 IPSys 名称、视觉资源与可授权的图标；不追求逐像素复制微软专属资源。
3. **文件管理呈现与业务语义分离**：UI 可将 Folder 显示为文件夹、将 FileLink 显示为文件；虚拟模块根不一定对应数据库真实 Folder。数据库绝不退化为磁盘明文目录树。
4. **底层数据沿用现有模型**：SQLCipher V2 folders / files / file_versions / file_objects / file_chunks / folder_file_links；FolderId、FileId、LinkId 和不可变版本语义保持，工作区 company/personal 独立。所有附件字节仍在加密数据库内。
5. **业务规则不因界面统一而放宽**：合同必须隶属于项目；公司业务档案目录/记录可按既有规则嵌套、混排、持久排序；个人/公司不能无确认跨空间共享物理字节；系统保护目录不能重命名、移动或删除；不能上传没有所属业务记录的游离文件。普通业务文件夹在 V2 中不是任意可嵌套目录。
6. **真实操作、真实反馈**：同一动作由统一命令定义和能力判断驱动顶部栏、行内“更多”和右键菜单；没有后端能力、业务规则禁止或当前任务锁不允许时隐藏/禁用并说明原因。禁止出现只有外观、没有真实功能的按钮。
7. **对现有用户保留可回退路径**：整个重构只落在 work/onedrive-file-manager；main 不变，不提前移除旧正式页面。所有阶段使用临时测试库和虚构测试资料，已确认的用户数据库不用于破坏性开发测试。

### 2.2 已知真实约束

- 当前 FolderKinds 仅支持 project、contract、ip、archive、archive_folder、general；ResourceSchemaV2.cs 的 CHECK/TRIGGER 严格限制 parent_id，不能把任意项目、资质、知识产权直接拖入其它目录。**第一阶段不改 Schema**。
- 现有 archive 的 entries/reorder 可实现目录和业务记录同表混排、任意持久排序；其它业务模块目前不是同样的任意混排 API。新文件管理器必须通过不同 provider 返回统一行模型，而不能误称后台已全模块支持相同排序/嵌套。
- 附件共享可能为同一个 FileId 对应不同 LinkId；仅删除一个可见文件行不应误删其它记录的共享原件。File 版本不等于 Folder 版本。
- 当前网页单击附件行可预览，与 OneDrive 单击选中、双击打开的习惯不同。本次明确将 **单击行选中、双击打开** 设为新 Explorer 的统一交互；只在新页面生效，旧 UI 不提前改变。
- 现有 Windows CI 仅在 main 的业务源码路径 push 时自动运行；新的分支必须单独安排相同门禁，否则“分支代码已提交”不等于“已通过测试”。

## 3. 开源选型及首阶段闸门

### 3.1 候选与许可

1. 第一候选：Saifullah-dev/react-file-manager，npm 包 @cubone/react-file-manager；React 组件，MIT；已有列表/网格、面包屑、左右导航、选择、工具栏、右键、拖动、复制/移动、简体中文及对外事件回调。
2. 第二候选：harryy2510/react-file-browser，MIT；存储适配器与业务元数据扩展较明确，可替换第一候选，但仓库较新。
3. 微软 Fluent UI：参考微软设计语言，为 IPSys 专用外壳、按钮/菜单/详情面板提供样式和可选组件；不得把它误当文件浏览器，也不默认使用有额外授权限制的资产。
4. 各候选引入前必须逐项检查具体版本的 LICENSE、第三方依赖许可证、是否可离线打包、bundle 大小、键盘与中文、API 自定义能力。记录 exact version、上游 commit、许可证 NOTICE 和本地补丁清单。不可直接复制许可不明的 OneDrive Clone。

### 3.2 P0 选型验证必须完成的 10 项

1. 能在现有 C# localhost 页面挂载，同时保留登录和工作区切换。
2. 列表布局接近用户 OneDrive 截图，支持可关闭/自定义的左栏与右侧属性面板。
3. 单击选中、双击打开、Ctrl/Shift 多选与右键位置一致。
4. 支持业务模块虚拟根，并在同一列表呈现真实文件与业务文件夹。
5. 公司业务档案目录与记录可以 **自由混排且保持用户排序**，不被组件强制“文件夹始终置顶”；若组件无法配置，则须验证可控的本地补丁，否则淘汰。
6. 可同时维护 LinkId、FileId、FolderId、version 等独立标识，文件名可重名，名称变化不破坏身份。
7. 顶部操作栏、菜单均支持由外部统一 CommandRegistry 注入动作/权限，而不是两套各自执行的动作逻辑。
8. 原有 8 GiB 分块/流式上传及 SHA 重复内容确认可以接管组件默认上传处理；不可转为纯前端整文件入内存。
9. 打包产物可全离线嵌入 Release 单 EXE，用户在 Visual Studio 里构建、使用无需配置 Node/独立前端服务；依赖可由 CI 安全构建且有版本锁。
10. 组件依赖、重写比例、维护成本、许可证有可审计证据，并出具首选/备选选择结论。

闸门：对两候选打“直接支持/需要可维护扩展/不能满足”三档；第 4、5、6、7、8、9 条任何一条不能可靠实现，则不能直接全面采用该组件。通过后冻结具体组件、版本及本地适配路线；在 P0 结果出现之前，**React File Manager 只是首选评估对象，不是必须采用的最终依赖**。

## 4. 新版统一信息架构

### 4.1 页面壳与导航

- 顶栏：IPSys 品牌/当前加密数据库状态、全局搜索、工作区切换、设置/关闭数据库；关闭数据库只锁库退出会话，不能停止 WinForms 服务。
- 左栏：个人资料、公司资料，选择后展示对应业务入口；保留企业资质、业务档案、公司项目、知识产权、综合资料、个人分类、回收站与设置。导航条目是虚拟目录或具体业务范围，不强制全部落成物理 Folder。
- 命令栏：返回/前进、创建、上传、下载、复制、移动、重命名、删除、更多；依据当前选中集合和后端允许能力即时变更。可由宽屏单行自动折叠到“更多”。
- 面包屑：从工作区根、模块、上级真实目录一路导航；支持返回上层和浏览器前进后退；不能以当前文件名字符串代替稳定资源 ID。
- 主视图：默认列表，提供网格切换（若候选通过），文件夹与文件混排。表头主列名称、修改时间/业务日期（明确语义）、类型、大小、状态/操作；无可靠字段的列使用“—”，不伪造大小/修改时间。
- 右侧详细信息：可开闭，单选展示记录/文件基础字段，类型化业务属性（项目编号、合同金额、专利申请号等）、关联、文件版本/来源；多选只展示数量与可执行批量动作。详情编辑调用既有业务 API/表单，不创建第二份数据。
- 宽窄屏：以内容容器宽度布局，防止多分辨率/125%/150% 缩放出现按钮挤压、名称逐字换行；长名称优先并用省略与悬浮完整提示。

### 4.2 行对象与操作语义

| 对象 | Explorer 呈现 | 进入方式 | 详情/操作特点 |
| --- | --- | --- | --- |
| 虚拟业务入口 | 文件夹式模块行/左侧导航 | 点击打开模块 | 不是真实 Folder，不能按物理 Folder 删除/移动 |
| 业务记录 Folder | 文件夹行 | 双击进入记录容器 | 单选后右侧查看、编辑业务属性，合同仅隶属于项目 |
| archive_folder 分类 | 普通目录行 | 双击进入 | 能按已有规则重命名、移动、排序，系统目录受保护 |
| 当前 Folder 下关联文件 Link | 文件行 | 双击预览/下载 | 使用 LinkId 作为“所在目录的可见实例”，FileId 保持版本/原件身份 |
| 历史版本 | 版本历史子视图 | 显示/下载指定版本 | version 与 FileId 关联，不假装一个新的独立 Folder |

首屏试点选 **公司业务档案**：它已具备最典型的“分类与资料混排、排序、递归导出”的接口。完成后拓展公司项目（项目→合同+附件）及知识产权，再拓展个人工作区和其它模块。业务属性面板应做到“同壳不同字段”。

### 4.3 交互统一契约

1. 单击行：选择；单击空白：清除；Ctrl 切换单行选中，Shift 连续范围选中，全选以当前可见层为准。文件夹、文件采用一致的选择高亮。
2. 双击目录：进入；双击可预览文件：预览；不能预览则明确提供下载。Enter 激活当前选中，Esc 关闭菜单/弹窗，Delete 打开二次确认，Ctrl+C/X/V 根据操作能力受控执行。
3. 右键：先处理行的选择状态再打开上下文菜单；顶部/行内/右键统一使用同一命令 ID、权限验证与事件处理。禁用行为给出清晰原因，不能触发伪动作。
4. 重命名：明确区分 Folder.name、File.name 与特定 Link 的 display_name，不因修改当前目录内显示名擅改共享原件的全局文件名；需经 UI 和 API 的精确定义验证。
5. 复制/移动：区分“只移动文件关联”“复用 FileId”“创建新 FileId 且复用 FileObject”“跨工作区独立复制字节”；模糊时必须出现清楚的选项，不允许一个“复制”按钮隐式改变共享语义。
6. 删除：Folder 记录软删除、文件关联解除/软删除、回收站永久删除和共享原件的最后引用回收分别调用正确接口；不得把行删除直接当物理数据块删除。
7. 大任务：重用现有上传进度、任务互斥、跨工作区切换提醒、删除进度、数据库压缩锁；禁止在任务中擅自切换工作区/关库，也不能在菜单上显示虚构进度。
8. 文件版本：Folder 无版本，File 有版本；默认选中当前版本，版本历史只在对应文件操作中显示并可下载特定版本。
9. 业务关联：IP 材料类别、合同归属、项目整体导出、Excel 台账等仍按现有业务规则工作；额外动作放类型化侧栏/菜单，不在浏览器内重复实现各套列表。

## 5. 前端与后端契约设计

### 5.1 推荐模块边界

- ExplorerShell：顶栏、侧栏、面包屑、右侧详情面板及新/旧 UI 共存入口。
- ExplorerView：第三方文件浏览器，仅接收数据、选中状态、命令状态及事件。
- ExplorerProvider：将“当前 workspace + virtual/root/folder location”转换为列表数据，禁止前端直接构造 SQL 查询。
- NodeMapper：把 ResourceRef/FolderDescriptor、FileLink、File/Version 映射为稳定 UI Node，不以名称或显示路径充当唯一键。
- CommandRegistry：统一定义命令 ID、名称、图标、禁用原因、适用选择集合、执行及刷新策略；顶部栏、右键、更多菜单全部复用。
- BusinessInspector：根据 Folder.kind/section 显示原有业务字段及已有编辑表单；只处理字段，不重复实现一套文件表格。
- TransferBridge：接管现有上传/下载/ZIP/导出/选择重复内容与任务状态；文件管理组件只负责呈现和派发命令。
- Adapter/API Gateway：只调用 IPSys 本机 /api/v2 和少量新增统一接口，不直接操作数据库，不替换 C# API 身份验证/Origin 限制。

### 5.2 稳定标识协议（示例，不意味着现有 API 直接输出）

ExplorerNode 包含：nodeKey（由 workspace + node type + 实际 ID 组成的稳定字符串）、workspace、nodeType（virtual-folder/business-folder/archive-folder/file-link）、folderId?、fileId?、linkId?、kind?、section?、parentNodeKey?、name、size?、modifiedAt?、sortPosition?、capabilities、businessMetadata?。

- folder 节点以 workspace + kind + FolderId + 必要 section 标识；虚拟目录以独立 virtual: 命名空间标识，不能伪造 FolderId=0 当真实资源。
- 文件行必须标识 LinkId；同一 FileId 出现在两个 Folder 下时是两个可见节点，不会因为去重而少一条行。
- 服务端必须是权限/业务约束的最终裁决者；前端 capabilities 只是提升体验，不能代替后端校验。
- API 错误统一解析 400/401/403/404/409/413/507、锁状态、超时及取消；写入成功后以服务端返回为准，不做仅本地 DOM 改变的假成功。

### 5.3 可复用端点及待补契约

| 操作范围 | 现有依据 | 新适配需要 |
| --- | --- | --- |
| 分类与文件夹 | /api/v2/folders/{workspace}/{kind}、详情、move、entries/reorder | 同一 provider 聚合虚拟层和真实 Folder；archive 与其它 kind 的能力不同 |
| 文件列表 | /api/v2/files/{workspace}/folders/{folderId}/links、现有 UI 聚合接口 | 返回 FileLink 及当前有效版本元数据，明确空目录、分页/排序与重名 |
| 上传与去重 | 原生 /api/v2/files/{workspace}/...、ip-v2.js 的 prepare/resolve | 继续逐块/流式；未发现重复自动归档，重复内容显示已有文件名与所属路径后选择；新 UI 只接管操作外壳 |
| 复制/移动/关联 | NativeFileCopyEndpoints、NativeFileLinkEndpoints、NativeGeneralTransferEndpoints、NativeIpTransferEndpoints | 建立类型化命令分发；缺失的目录范围操作需补新接口并先测试 |
| 删除与恢复 | 现有 Folder 删除、Link unlink/restore、RecycleStore 和 purge | 依据 nodeType 分发，删除共享引用后验证其它目录仍能读取 |
| 搜索 | SearchStore 与跨模块 UI 搜索 | 结果包含可回到原位置的资源身份，不能跨工作区泄露 |
| 版本与预览 | FileVersion、现有下载和 PDF/图片/文本预览 | 历史版本入口与旧预览行为一致；Office 原件不声称本地有 Microsoft 365 在线编辑 |
| 批量导出与 Excel | 现有模块导出及 ExcelLedger | 文件/目录选择递归导出与 Excel 台账导出分开；保留项目包含合同规则 |

**缺口先填“接口适配差异表”**，不能预先假定目前每个虚拟目录都有新增、重命名、移动及同序排序能力。缺口应由服务端实现并覆盖测试，不通过浏览器端编造成功记录。初期不增加通用 schema kind、不做任意文件夹嵌套；如确需突破现有目录结构，单独走结构变更评审并在测试库实验。

## 6. 构建、部署与兼容策略

1. 源码允许新增隔离的 frontend/ 或 src/IPSys.Frontend/ React 工作区、依赖锁文件和本地打包脚本；不能把 Node 进程当作 IPSys 运行时依赖。
2. 开发机器继续可仅使用 VS 编译和调试 C#：通过 CI 构建并提交/固定审计后的前端产物，或经验证的受控资源生成策略，供 .csproj 以 EmbeddedResource 编译。具体策略在 P1 技术验证后确定，**必须验证离线 VS Debug 和 Release 单 EXE 均可运行**。
3. Program.cs 维持仅本机绑定、Host/Origin 校验和所有敏感操作会话授权；不得从互联网 CDN 加载 React、CSS、字体或图标。静态资源可设置缓存策略但切换版本须可验证。
4. 新 Explorer 在开发分支以功能开关/专用路径运行，保留原正式页面可回退；先共存，逐模块切换，最后只有用户确认时才处理旧界面清理。
5. 不并行维护两套业务存储服务。对外 MCP、Excel、回收站、数据库压缩均继续调用原有业务层，前端重构不得改变其资源身份与已有工具语义。
6. 保留简体中文、键盘可操作、无障碍标签和完整错误反馈。鼠标右键不能是唯一操作途径；“更多”菜单覆盖同样功能。

## 8. 测试矩阵与可重复验收

### 8.1 核心场景

| 类别 | 最低测试案例 |
| --- | --- |
| 导航 | 个人/公司切换；虚拟根/真实 Folder/业务记录；面包屑；浏览器前进后退；无权限/被删目录 |
| 列表 | 文件夹/文件混排、手动排序及刷新持久化、长文件名、空目录、上千条分页/虚拟滚动验证 |
| 选择 | 单选、Ctrl/Shift、全选、右键后选中语义、跨目录选中清空/保留规则、禁用动作 |
| 命令 | 顶栏与右键同一 ActionId；重命名冲突；复制/移动合法与非法目标；失败/取消可回退 |
| 文件 | 0B、小文件、PDF/图片、>2 GiB 真实测试原件；上传中切换工作区/关库/断开请求 |

| 密钥与锁 | 解锁/关库/会话恢复、Host/Origin 约束、任务互斥、数据库完整性与压缩后的旧/新界面正常读取 |
| 离线发行 | 不可访问互联网时启动；C# VS Debug；win-x64 单 EXE；无 wwwroot 外部依赖、无 CDN |

### 8.2 视觉与使用体验

- 固定用户所提供的 OneDrive 截图为界面参考，采集相同信息密度的自有测试页面快照。交互以“功能行为一致”为首要指标，不以微软标识或精确像素克隆作为目标。
- Edge 和 Chrome：至少 1366×768、1920×1080；Windows 缩放至少 100%、125%、150%。逐项检查导航高度、命令栏换行、列表头/行高、名称省略、弹窗位置、面包屑与侧栏/详情面板响应式。
- 保存带有典型长中文项目名、长英文附件名、0 份与多份附件、同 FileId 多 Link 和多版本的**合成数据**截图。审查人员需能够把同类组件的截图并排检查，避免“项目改了合同没改”。
- 同一公共组件修改后至少覆盖：公司档案、项目/合同、知识产权、企业资质、个人记录以及文件版本菜单；运行统一回归而非只检查当前页面。

### 8.3 自动化与分支 CI

- Windows .github/workflows/web-windows.yml 目前 push 触发仅 main。P1 应在新分支增加相应触发或明确的 workflow_dispatch 检查（不修改 main），使后续**每个有实质代码的阶段**都有受检查的 Windows Debug/Release、嵌入资源、WebSmoke、原 Node 测试及 React 新测试。
- 新 UI 增加真实浏览器 E2E（如 Playwright，开发依赖仅留 CI）验证导航/多选/键盘/右键/上传错误/业务字段；截图记录不得包含真实个人或公司文件名。
- 接口测试使用临时 SQLCipher 测试库；性能基准用合成记录与模拟大附件，实测报告必须标注设备、测试数据量和时间。
- CI 成功不能替代人工视觉验收，人工验收也不能代替服务端约束及内容完整性测试。

## 9. 数据安全、回滚和故障边界

1. **测试资料库专用**：重构测试不得连接正式资料库；任何 Schema 实验都在新建测试库进行。用户历史已说明开发期暂无必须迁移的旧正式库；仍须维持现行数据身份/读取契约，不能依赖“反正是测试库”而弱化测试。
2. **事务/幂等**：移动、复制、去重引用、版本提交以及批量删除必须沿用服务器端事务/任务控制；重复点击、网络超时和 UI 刷新不得产生二次写入或误判成功。
3. **空间与大文件**：8 GiB 上限、流式 IO、磁盘预检及用户可见进度按现有后端为准；禁止 FileReader 整个加载进前端内存，禁止假百分比。
4. **资源生命周期**：锁库后销毁前端敏感状态、停止未授权轮询；PDF/图片对象 URL 及时释放，窗口关闭时 FileTask/WinForms 的安全退出规则不变。
5. **回滚以提交为单位**：所有后续提交只落开发分支，阶段完成记录可工作的 commit SHA；问题出现使用 git revert 或重新切到已知正常的提交进行验证，不用强制推送覆盖历史。用户需要继续旧版时使用 main 即可。前端恢复不等于数据库变更自动回滚，所以初期严格禁止 schema 改动。
6. **分支合并条件**：完整功能矩阵、CI、人工验收及数据核对通过后，先提供 main 与开发分支差异、第三方许可证清单、风险与仍未完成事项；只有用户明确要求才合并，不自动 PR、不自动合并。

## 10. 项目管理及持续维护

- 本文件是专用重构计划；REQUIREMENTS.md 仍维护业务需求，UI_BASELINE.md 与 UI_COMPONENT_MATRIX.md 在每个阶段实际改变时同步更新；不得为了新效果未经确认直接覆盖已冻结业务约束。
- 每一阶段的提交说明必须包含：当前操作、用户指令、具体修改、遇到问题、后续避免问题、最终结果，并记录所用依赖版本与对应测试结论。AIGT-templates/AGENTS.md 与 AI_RULES/GIT_OPERATIONS.md 为每次实质性操作的基础必读入口。
- 严格区分“已实现”“自动测试通过”“真实浏览器通过”“用户确认”；未验证的事项标记待验收，不用笼统的“完全复刻”表述。
- 版本与产品边界变化（例如完全自由嵌套、任意记录移入其它模块、对外共享、远程同步、多人协作、云端 Office 编辑）必须新增单独需求评审。当前阶段不包含这些功能，也不以灰色禁用按钮冒充支持。
- 如发现首选开源组件对混排、选中行为或业务能力拓展存在长期难以维护的核心冲突，应在 P0/P1 阶段果断切换备选或采用自研薄壳，避免为了保留既选组件持续制造特例。
