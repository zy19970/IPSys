## 第五轮：核实删除与空间回收的额外磁盘开销

### 用户原始消息

现在有一个问题，因为之前重点解决的一个事儿，就是说我在删除的时候，或者说我在空间整理的时候，不要出现再要额外空间的情况，现在这个问题解决了吗

### 核查依据及结果

1. 基于主分支 `fba6b3d` 核查 `Vault.cs`、`VaultCompactEndpoints.cs`、`RecycleStore.cs`、`NativeFolderStore.cs`、`NativeArchiveStore.cs`、`NativeFileLinkStore.cs` 及前端设置。原地回收只对实际 INCREMENTAL 的库开放，后台独立执行每批 256 页的 `incremental_vacuum`。预检公式为 256 页字节数加 64 MiB，典型 4 KiB 页约 65 MiB。旧 NONE 模式库不自动迁移，设置回收入口禁用。完整 VACUUM 保留后端通道，预算为 2 × 库文件大小 + 128 MiB。
2. 普通删除只修改 Folder 或 Link 的软删除标记。永久删除只有最后引用解除时才物理删原件数据。异步大文件清理每 32 个 chunk 更新进度，却在 `RecycleStore.Change` 一次事务内，提交前各批仍受统一 rollback journal 保护。永久删除不自动启动文件收缩。事务所需余量依赖数据页，与回收的约 65 MiB 预检是两件事。
3. SQLite 官方数据库文件格式和加锁文档确认回滚日志保留事务前数据页。一次普通 SQLite 3.53.1 的临时样例使用 4 KiB 页、DELETE 日志、FULL 同步、INCREMENTAL、secure_delete=ON，对 64 个 1 MiB BLOB 在同一事务中分两次删除，未提交日志从 32.18 MiB 增至 64.33 MiB，提交后日志消失，数据库文件大小不变。此结果仅示范同一事务分块无法约束日志大小，不代表 IPSys 真机、SQLCipher 或大库实测。
4. 确认 Windows CI #44436045933 对 `e394dec` 成功，其 SQLCipher/HTTP 步骤覆盖永久删除任务与回收。生产库、实际磁盘近满、真实 20–50 GB 大库的临时空间峰值未测。本轮发现 `interactions.js` 中设置悬停和确认文本，以及 `McpLocalVault.cs` 的回收工具描述仍误用「不需要额外磁盘空间」，实际以后端校验为准。本轮仅评估并归档。

### 拟交付回复

之前担心的「整理时还要按整库大小预留空间」已解决，适用于支持增量回收的资料库。磁盘余量为零时，大批永久删除和空间回收仍可能做不了。普通删除只改状态，数据库文件通常不缩小。回收站永久删除会释放库内可复用页，分批执行 SQL 仍共用一笔事务，回滚日志可随删除量增长。设置里的空间回收按 256 页在原文件内进行，4 KiB 页时需要约 65 MiB 可用空间作为预检；旧库 NONE 不自动迁移。用户实际库模式仍需以设置页为准。界面「不需要额外磁盘空间」与真实预检不一致。Windows CI 通过回收和永久删除相关烟测，真实大库和磁盘将满未实测。
