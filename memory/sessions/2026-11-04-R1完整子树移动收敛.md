## 技术决策

旧 schema 3 的 `folder_parent_update` 要求父级 deleted=0，故不能直接更新隐藏 D3 的 section；原 `NativeArchiveStore.ListAll` 仅返回当前可见目录，遗漏 deleted D2 及其隐含后代。只移根节点会产生跨模块错归属，恢复后不可见并使永久清理受阻。

采用开发阶段允许的 schema **4** 新库，不自动迁移旧 3 库，不触碰已有资料库。仍保留 `ResourceSchemaV2.cs` 历史文件名。新触发器仅在更新目录 section、parent_id 没变、deleted 没变、原父级为 archive_folder 且已更新为同一目标 section 时，允许被软删的直接父级；其他重新挂载与非法父级继续拒绝。普通 `folder_parent_insert` 原规则不变，闭环/跨区约束仍有效。用 Python 内存 SQLite 实际演练相同触发器 SQL，确认对已删除父级的普通 reparent 拒绝，父优先迁移成功，第三层临时触发器 RAISE(ABORT) 后整个事务可回滚（只是 SQL 层预验证，绝非 SQLCipher Windows 实验）。

`NativeFolderBatchTransferEndpoints.Execute` 对同区跨模块原位移动，在开启写事务前使用 parent_id 的递归物理树（含已删除及隐藏但未删的后代）按 depth/id 顺序收集并核对 workspace、kind、原 section、计数上限和批量重叠；移动父级后顺次更新所有后代，删除原先“计数不同就拒绝”的暂行保护，保留原 FolderId/parent_id（根除外）及所有 FileId/LinkId/文件版本，deleted 状态保持不变。相同 section 的原位移动以及共享、独立复制继续原先的仅活动内容逻辑，不扩大改动范围。

`ResourceSchemaV2Smoke.cs` 需要覆盖 D1/D2(deleted)/D3(active) 原位移动、移动前第三层失败注入必须完整回滚、跨模块后回收站显示正确 section、恢复后完整目录可见与附件双版本关联仍完整、另一个模块方向成功移动后永久清理完整墓碑子树；旧 2/3 版本拒绝而不迁移。活跃 `t-http.cjs` 新增真实 project→general 同样顺序的移/恢复/两版下载，以及 general→achievement 之后永久清理，纳入 `result-gate.cjs` 必须 PASS；现行 Edge 的既有 14 个测试仍应全部 PASS。
