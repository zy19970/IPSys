### 代码定位及原因

1. `src/IPSys.Web/SessionEndpoints.cs` 的 `GET /api/check` 会持有 `Vault.Gate` 同步执行 `PRAGMA integrity_check;`，然后 `SELECT count(*) FROM file_objects WHERE state='writing'`，设置 `runIntegrityCheck` 直接等待这个请求，无法提供中间进度。且 `interactions.js.startSession()` 在恢复登录时竟会用这个耗时接口作为 token 校验。

## 第九轮：2026-11-06 对 500 GB 硬盘存储容量的担忧

### 用户原始消息

> 我现在有些后悔用这个数据库了，这样的话我500G的硬盘也就存储250G的内容

### 代码依据与已向用户说明的事实

核查 main `a26c29eafaee54c1dba542ccd2acda033e80468f` 的 `src/IPSys.Web/VaultCompactEndpoints.cs`，当前 `VaultCompactStore.Inspect` 的额外空间门槛是 `fileBytes*2+128MiB`，还分别要求数据库所在盘和系统临时目录所在盘的空闲容量都满足。这仅是手动执行完整 `VACUUM` 前的保守空间校验，不代表 SQLCipher 数据文件本身重复写入两份，也不影响无 VACUUM 情况下继续存入超过 250 GB 的数据（仍要为日常写事务和日志留空闲）。

在纯演示 500 GB 空盘上，如果用户要求同一磁盘上的数据能够随时满足这项完整压缩校验，需要 `3*DB+128MiB<=500GB`，即数据库理论上最多约 166 GB，实际还受到系统/文件系统和日常写入空间约束。由此承认用户担忧根源真实存在（容量回收机制的全库重建临时空间代价），但不是“资料库天然只有250GB容量”。删除后内部分配的 `freelist` 页面仍会被下一次写入复用，故不必频繁 VACUUM。

官方资料核验：SQLite VACUUM https://www.sqlite.org/lang_vacuum.html 说明复制临时数据库 + 回滚日志可能至多额外耗用原 DB 2 倍空间，VACUUM INTO 可指定另一个目标文件而避免回写原文件那一步；SQLite PRAGMA https://www.sqlite.org/pragma.html 说明 `auto_vacuum=INCREMENTAL` 可以释放整页并缩小物理 DB，不能完全消除碎片，需在建表前配置，旧 none 库切换需要一次 VACUUM。对于 SQLCipher 实际配置及大文件 BLOB 安全性**尚未进行专项测试**，不能直接保证在 IPSys 中可用。

### 本轮结论与实施边界

没有必要仅因为当前完整压缩需要额外临时空间就立刻更换数据库。建议将下一阶段的评估聚焦于：是否在新库启用增量回收、怎样确保老库升级的无损性、是否支持使用其他物理磁盘辅助全库压缩（含 SQLCipher 密钥及校验）、如何设置性能/空间告警。保持单加密 DB、共享版本/FileId/LinkId 等既有设计的前提下先做可复现测试，而非直接改写大库逻辑。此轮用户是在表达担忧和讨论方向，未明确授权改变业务代码，故只解释方案并按 Memory 协议归档，不修改源代码/数据库/发布流程，也不执行新 CI。

### 拟交付用户的核心回复

明确 500GB 不等于 250GB 存储上限，完整同盘 VACUUM 的现行安全预留甚至在500GB示例中限制可压缩 DB 最大约166GB；日常写入和内部空闲页复用独立。SQLite 官方有 incremental_vacuum 等可研方向，但需要在 SQLCipher/现行文件结构中验证，不宜直接迁库；推荐评估更合理的空间回收机制，保留安全和单 DB 目标。


## 第十轮：2026-11-06 非加密 SQLite 与 INCREMENTAL 风险评估

### 用户原始消息

> 两件事情，第一件事，如果用非加密的会不会好一些。第二件事INCREMENTAL这个风险大不大

### 核实依据与分析

重新读取 AIGT 规范和 IPSys Memory/本会话，核查 main `06ff0e7b99df008de597e3fea5172d1652a9f4e9`。`Vault.cs` 的 `Connect` 强制 SQLCipher、无 plaintext 降级；`PRAGMA journal_mode=DELETE` / `synchronous=FULL`，`ResourceSchemaV2.cs` 的 `file_chunks` 保存二进制原件块、`file_objects`/版本/共享保护；`VaultCompactEndpoints.cs` 标准 `VACUUM` 的额外空闲空间检查 `fileBytes*2+128 MiB`。SQLite 官方 VACUUM https://www.sqlite.org/lang_vacuum.html 表明 plaintext SQLite 也需要最多额外约两倍大小，不是 SQLCipher 造成；SQLCipher 官方设计 https://www.zetetic.net/sqlcipher/design/ 明确 per-page IV/HMAC 等空间消耗，性能 https://www.zetetic.net/sqlcipher/performance/ 标注部分负载加密额外处理 5–15% 但不是磁盘空间比例。因此换非加密会略减体积与 CPU 成本、牺牲保密性，不解决主要 VACUUM 空间门槛。

SQLite 官方 PRAGMA https://www.sqlite.org/pragma.html 表明 `auto_vacuum=INCREMENTAL` 为原生机制，建立指针映射可回收完整空闲页并截断 DB，未能整理部分填充页，可能增加碎片；无自动释放需调用 `incremental_vacuum(N)`；现有 NONE 库不能仅设置参数就生效，须首次建表之前设定或先完整 VACUUM。SQLCipher 源码 https://github.com/sqlcipher/sqlcipher/blob/master/src/pragma.c 可见 AUTOVACUUM 分支，但 **尚未真实在 IPSys 当前 SQLCipher 二进制和大 BLOB 场景验证**。风险分层：SQLite 引擎本身低；ISys 集成/大型删除+事务与版本共享中等；对现有 NONE 数据库无备份地转换模式中高；长期性能碎片影响中等。不会主动改变业务 FolderId/FileId/LinkId，但需验证数据完整性。当前 SQLite DELETE journal+synchronous FULL 是安全基础，不等于断电测试已通过。

### 推荐与实施边界

保留 SQLCipher；先在仅供测试的新建独立加密库，在建表前设置并复核 `PRAGMA auto_vacuum=INCREMENTAL`，用不同大小 BLOB 与多版本/共享/回收站物理清理验证 `page_count`、`freelist_count`、文件体积、SHA256、`integrity_check`、`foreign_key_check`、反复打开/异常终止恢复、写入时延和文件碎片。在空闲时分批 `incremental_vacuum(N)`，并使用原有 Vault.Gate/排他任务机制；禁止每次删除就进行长耗时自动回收。仅在测试表明值得且无安全回归后，提出新库默认增量的正式代码改造方案；已有库迁移另行评估与备份确认。不建议直接取消加密、强行修改现有 DB 或简化事务保护。此轮没有修改产品代码/数据库、没有运行大 BLOB SQLCipher 专项实验。

### 本轮对用户的可见答复要点

已经解释：非加密 SQLite 仍有相同的完整 VACUUM 临时空间问题；加密的额外磁盘开销是每页 IV/HMAC 辅助数据，不是 DB 体积翻倍。INCREMENTAL 原生机制风险较低，真实 IPSys 集成属于中等工程风险、旧 NONE 库切换需完整重建。建议加密不变、先测试新库增量回收与文件版本共享引用。
